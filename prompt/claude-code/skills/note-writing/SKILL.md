# note執筆

note本文の規範を増やさず、既存の知識源とskillを一つの執筆工程へつなぐ。

## 責務境界

- 文章構造と論証は`japanese-tech-writing`を正本にする。
- 具体性、リズム、AIらしい空句の点検だけ`natural-writing`で補う。
- `decision-writing`からは事実性、リンク、`content-lint.py`だけを継承する。意思決定資料の構造は記事へ持ち込まない。
- 関連するCosenseは`scrapbox-context`で読む。書込み時は`save-to-scrapbox`のpreview、承認、readbackを通す。
- 人脈候補と連絡文面は`ask-network`へ委譲する。送信は各媒体skillの承認境界を守る。
- 公開操作は下書き保存と分離し、実行直前に明示承認を得る。
- 操作上の罠は`self-learn`でClaude memoryへ残す。著者の思想や眼差しはCosenseへ残す。

詳細な台帳項目、出典分類、眼差しの初期候補は[article-contract.md](references/article-contract.md)を必要時に読む。

## 正本

正本を増やさない。

| 対象 | 正本 |
|---|---|
| 公開本文、公開日時、公開状態 | noteの公開ページ |
| 記事の問い、資料、判断、先方確認、共有履歴 | 記事ごとのCosenseページ |
| 全記事に再利用する眼差しとvoice corpus | `tkgshn-private`の`note執筆` |
| メール、Beeper、Claude Code、Codexの会話全文 | 各ネイティブログ |
| 公開指標の時系列 | `note_key`をjoin keyにした追記型snapshot |
| 手順、文体、論証の恒久規則 | shared skill |

Cosenseへ公開本文や私信全文を複製しない。要約と証拠へのpointerだけを置く。

## 執筆フロー

### 1. 記事台帳を見つける

Cosenseで既存の記事ページを探す。

既存ページがあれば、別名のページを作らない。

公開済みならnoteの`note_key`を同一記事のjoin keyにする。

### 2. ソースを集める

最初から本文を書かない。

次の順で、記事の問いに関係する範囲だけ集める。

1. 本人が書いたCosense、メモ、過去記事
2. Claude CodeとCodexの関連対話
3. 公開資料と一次ソース
4. 本人の観察、ライフログ、現地資料
5. 他者の発言、取材、私信
6. AIによる要約や推論

過去画面しか手がかりがない場合だけCoastを使い、候補を元データと照合する。

長い会話や資料は記事へ丸ごと入れない。主張を支える箇所と、参照先だけを台帳へ置く。

### 3. 出典を分類する

すべての主張を次のどれかへ分ける。

- 公開資料
- 本人の観察または発言
- 他者の発言
- AIによる整理
- 未確認

他者の私信や録音は、取得できたことと公開してよいことを分ける。

引用、写真、数値、肩書きには、出典と公開条件を持たせる。

### 4. 本人の問いを作る

本文の前に、次を短く書く。

- 何を見に行ったのか
- 最初に何だと思っていたのか
- 現場で何がその仮説を裏切ったのか
- 何が何へ変換されていたのか
- 壊してはいけない既存の強さは何か
- それでも変えるなら、どこか
- 最小の実験は何か

現場が仮説を裏切らなかった記事では、反転を捏造しない。

### 5. voice corpusを選ぶ

その記事で本人が手書きした段落を最優先にする。

次に、主題と距離が近い過去記事の本人執筆部分を二、三箇所選ぶ。

記事全体がAI支援を受けている場合は、公開本文をそのまま「本人の声」と断定しない。本人が書いた範囲、本人が直した範囲、AIが補った範囲を区別する。

語尾だけを模倣せず、対象を見る順序を再利用する。

### 6. 下書きを作る

観察、解釈、提案を混ぜない。

基本構成は次の順を候補にする。

```text
場面または違和感
→ 既存の営みの強さ
→ 自分の仮説が変わった理由
→ 情報や判断の変換過程
→ 自分の立場
→ 小さく可逆な実験
```

構成が素材に合わない場合は変える。型のために反転や提案を作らない。

抽象語は、現地の紙、机、画面、手順、身体感覚、数字へ一度接地させる。

技術や製品を先に置かず、ボトルネックと残すべき強さを先に書く。

### 7. ユーザーの修正を学びにする

修正後は、AI案とユーザー確定稿の差分を取る。

差分を次へ分ける。

- 事実の訂正
- 視点の変更
- 構成の変更
- 語彙または文体
- 倫理または公開境界
- 読者想定

記事固有の修正は記事ページに残す。

全記事へ昇格する基準は次のとおり。

- ユーザーが原則として明示したものは即時採用する。
- 二つ以上の記事で同じ修正が起きたものは安定ルールへ昇格する。
- 一記事だけの特徴は候補に留める。
- 相手や案件に固有のものは全体ルールへ昇格しない。

一回の修正から人格を推測しない。

### 8. 公開前に検証する

次を別々に確認する。

1. 事実と引用
2. 写真、氏名、顔、クレジット、転載条件
3. 先方確認が必要な内容
4. リンク切れとキャプション
5. noteの描画結果
6. `content-lint.py`のERROR=0

本文を保存したことと、公開したことを同一視しない。

公開は対象URL、公開内容、副作用をpreviewし、ユーザー承認後に行う。

### 9. 公開後を閉じる

公開URLを読み戻し、本文、画像、キャプション、リンクを確認する。

記事ページへ次を戻す。

- `note_key`
- 公開URLと公開日時
- 最終的な問いと立場
- 参照した資料と対話
- 公開条件と確認結果
- 修正から得た学び
- 共有先、目的、状態、native threadへのpointer
- 指標snapshotへのpointer

共有は、記事の当事者、引用元、実装上の対話相手を優先する。

新規連絡を乱発せず、関連する既存threadへ返す。

### 10. 指標を読む

「伸びた」を単一スコアへ潰さない。

- 到達：ビューまたはPV
- 共鳴：通常スキと匿名スキの合計、コメント、スキ率
- 行動：フォロー、リンククリック、返信、紹介、面談、再利用
- 速度：24時間、7日、30日の増分
- 寿命：30日、90日、365日の増分

標準ダッシュボードの「ビュー」とnote proの「PV」は定義が違う。同じ時系列へ連結しない。

snapshotには`source_surface`と`metric_definition`を必須にする。

公開APIは読取adapterであり正本ではない。公開状態は公開ページで確認する。

## 状態

状態を明示し、飛ばさない。

```text
source-collected
→ thesis-shaped
→ drafted
→ user-edited
→ fact-reviewed
→ preview-verified
→ publication-approved
→ published-readback
→ outreach-drafted
→ outreach-sent
→ responses-integrated
```

`drafted`は`user-edited`ではない。

`published`は公開操作の受理ではなく、公開ページのreadbackを終えた状態を指す。

`outreach-drafted`は送信済みではない。
