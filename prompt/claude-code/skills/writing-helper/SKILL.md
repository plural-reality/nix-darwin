# Writing Helper

完成文をすぐ生成せず、変更コストの低い構造から順に本人と決める。
このskillは「何を書くか、どの順で読ませるか」を進行する。文体、媒体固有の書式、公開操作は対応するskillへ委ねる。

## 進め方

### 1. 執筆条件を短く固定する

既知の情報を聞き直さない。
次のうち、構成を左右する未確定事項だけを一度に最大3問尋ねる。

- 読み手は誰か
- 読後に何を理解、判断、実行してほしいか
- 媒体とおおよその長さ
- 必ず入れる事実、体験、製品、リンク、行動喚起
- 避ける主張、公開できない情報、確認が必要な引用
- 本人の立場と、最も強い反論または読み手の疑問

質問には、なぜ構成に影響するのかを必要な時だけ一言添える。
本人が「質問不要」「まず案を」と言った場合は、仮定を明示して先へ進む。

### 2. 構造の異なるアウトラインを見せる

本文はまだ書かない。
通常は2〜3案を箇条書きで示す。見出し名だけを変えた同型案にしない。

各案には次を短く付ける。

- 中心命題
- 読者がたどる流れ
- 終わり方または行動喚起
- 強み
- 弱点、必要な根拠、想定反論

HP・LPなら、ページ内の順序、各セクションの役割、CTAまでをアウトラインに含める。
記事なら、導入、論証または物語の転換、反論、着地までを含める。

本人に、採用案、混ぜたい要素、削りたい要素を尋ねる。
返答が一部だけでも、残りを推測で採択せず、明示された修正を反映した次版を見せる。

### 3. 選んだアウトラインをplanへ変換する

採用した構成を、そのまま執筆の作業planとして管理する。
利用可能なtask plan機能があれば使い、なければ会話内に短い進行表を置く。

各セクションを次の形で箇条書きにする。

```text
- セクション名
  - この節の役割
  - 主張または伝える事実
  - 根拠、具体例、本人の経験
  - 読み手が抱く疑問または反論
  - 次の節へのつながり
  - 未確認事項
  - 分量の目安（全体の長さが指定された場合）
```

事実、本人の観察、他者の発言、AIによる提案、未確認を混ぜない。
根拠がない場所を一般論で埋めず、`要調査`または`本人の判断待ち`とする。

アウトラインを更新するたびに全文を見せる。
差分だけを出して、現在の全体構造を見失わせない。

### 4. アウトラインを確定してから本文を書く

本人が構成を選んだ、または「この構成で書いて」と示した時に本文へ進む。
明示がないまま、アウトライン案の一つを完成稿へ昇格しない。

本文は確定したplanだけを根拠に書く。
新しい主張、数字、引用、事例を勝手に足さない。
執筆中に構造上の問題や重要な欠測を見つけたら、滑らかな文章で隠さずplanへ戻して示す。

長い原稿は節単位で書き、各節を確認してから次へ進めてもよい。
本人が一括初稿を求めた場合は、確定したアウトライン全体から一括で書く。

### 5. 構造と文章を分けてレビューする

先に、次をアウトラインへ照合する。

- 各節が一つの役割を持つか
- 主張に根拠が対応しているか
- 同じ内容を別の見出しで繰り返していないか
- 反論や重要な限定を飛ばしていないか
- 導入で約束した問いを最後に回収しているか
- CTAが本文の内容から自然につながるか

構造が通った後で、媒体に合う文章skillを使う。

- 記事、ブログ、解説：`japanese-tech-writing`。noteの記事運用は`note-writing`
- 自然さとAIらしい空句の点検：`natural-writing`
- 意思決定を求める提案・相談資料：`decision-writing`
- HP・LPの画面設計やビジュアル：対応するWeb・デザインskill

関連skillを使う場合も、このskillで確定した主張、出典境界、アウトラインを変えない。

## 会話上の表示

進行中は、必要なものだけを次の順で見せる。

1. 今決める質問
2. 現在のアウトライン全文
3. 確定事項と未確認事項
4. 次に進むplanの一手

質問だけを長く並べて執筆を止めない。
一方で、本文を生成してから構成を事後承認させない。

## 完了条件

アウトライン作成だけの依頼なら、本人が選んだ構成、各節の役割、必要な根拠、未確認事項が一つのplanとして読める状態で完了する。

本文までの依頼なら、確定アウトラインとの対応、事実と未確認の区別、媒体別レビューを確認して完了する。下書き完成、保存、公開、送信は別の状態として扱う。
