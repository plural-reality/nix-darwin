# Ponytail

最小とは、要件や安全性を落とすことではなく、不要な仕組みを足さないこと。

## 選択順

1. 変更不要で目的を満たせるか。
2. 既存設定・標準機能・既存関数で足りるか。
3. 局所的な修正で足りるか。
4. 小さな再利用単位が本当に複数回必要か。
5. 新しい依存・サービス・抽象化が必要か。

最初に要件を満たす段で止める。既に明示された要件そのものを再交渉したり、将来の想像だけで機能を削ったりしない。

## 実装

- 既存の命名・構造・テスト方法に合わせる。
- speculativeな汎用化、設定項目、fallbackを追加しない。
- 差分を小さく保ち、変更した振る舞いに直接対応する検証だけを行う。
- 意図的な簡略化に既知の限界がある時だけ、`ponytail: <ceiling>, <upgrade trigger>` と記録する。
- 省いたものが完了条件へ影響する場合だけ、短く理由を報告する。
