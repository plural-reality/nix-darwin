# 定例メモ共有 runbook

この文書は `teirei-memo-share` の詳細手順。会議ごとに必要な部分だけ読む。ツールの認証情報や個別のIDをこのファイルへ保存しない。

## 1. 事実の抽出

Granolaのノートを上から読み、次のレコードへ正規化する。空の項目は作らない。

```text
meeting: 会議名
held_at: 開催日時（ノートにある値）
source: Granolaノートへのリンクまたは識別子
facts:
  - kind: decision | progress | request | open_question | date
    statement: 一文の事実
    actor: 発言者または決定主体（不明なら unknown）
    evidence: ノート内の位置・見出し・リンク
    certainty: recorded | inferred | unresolved
```

- `recorded` はノートに明記されたこと。
- `inferred` は複数の記録から導いた整理で、推論であることを明記する。
- `unresolved` は確認が要ること。日付・担当者・公開範囲を推測で確定しない。
- 参加者一覧や画面表示だけでは、発言・承認・送信の完了証拠にならない。
- Computer History のイベントは補助証拠。`computer_history_status` が使える環境では状態と時刻を確認し、`eventStreamRootPath/segments/*/events.jsonl` を会議名・アプリ名・URLなどで狭く検索する。該当ファイルが取得できない場合は「履歴なし」とせず、Granola/Docs/Beeperの正本へ戻る。

## 2. Granola のノートと定例フォルダ

定例フォルダは会議ノートを時系列で束ねるための索引であり、Google DocsやScrapboxの代替ではない。

1. 会議名・開催日で既存ノートを検索し、同名の定例フォルダがあればそこへ整理する。同名フォルダを重複作成しない。
2. フォルダを作る必要がある場合は、作成対象名と既存候補を示してから作成する。フォルダ名は会議の安定した名称（例: 「<案件名>定例」）にする。
3. 共有を変更する場合は、named member（collaborator / viewer）とドメインリンクの範囲を区別する。会議参加者全員へ自動共有しない。
4. 共有メンバー追加・リンク範囲変更は外部状態の変更である。対象、権限、副作用を直前にプレビューし、ユーザーの明示承認を得る。実行後はメンバー一覧とリンク範囲を読み戻す。
5. Granola内でGoogle Docsのアジェンダや関連ノートが紐づいている場合は、そのリンクを会議レコードに残す。リンク先の権限が受け手にあるかは別途Google Driveで確認する。

Granolaにtypedな読み書き窓口がない環境では、利用可能な公式UIだけを使う。画面のスナップショットで対象を一意に確認してから一操作を行い、各操作後に再取得する。blind keystrokeやユーザーの既存ウィンドウの整理はしない。

## 3. Google Docs の更新

法人の定例メモは `gws` で扱う。まず現在状態を取得し、別編集を検知する。

```sh
gws drive files get --params '{"fileId":"DOC_ID","fields":"id,name,mimeType,modifiedTime,lastModifyingUser,webViewLink,parents","supportsAllDrives":true}'
gws docs documents get --params '{"documentId":"DOC_ID"}'
```

更新規則:

1. 既存の会議日見出しと次の同レベル見出しの範囲を特定する。
2. 追加・置換するのはその会議ブロックだけにする。
3. `documents.batchUpdate` の `insertText` / `deleteContentRange` 等を、取得した index に対して実行する。本文全体を消して入れ直さない。
4. 他者の `modifiedTime` が読み取り時点から変わったら、候補を破棄して再取得する。
5. 実行直前に対象ID、変更範囲、挿入本文、共有範囲をプレビューし、ユーザーの当該更新への明示承認を得る（事前に同じ更新への承認がある場合を除く）。
6. `documents.get` で見出し、本文、リンク、必要なスタイルを読み戻す。APIのHTTP成功だけを完了証拠にしない。

会議ブロックの最小形（実際の内容に合わせて項目を削る）:

```text
YYYY/M/D 会議名
  決まったこと
  進んだこと
  依頼・確認待ち
  日付・次回
```

一文一行で書き、誰が何をしたかを主語で残す。未確定は「確認待ち」と書き、確定事項へ変換しない。

## 4. Scrapbox の更新

1. `scrapbox-context` で会議名・案件名・参加者名を検索し、既存の案件ページまたは日付ページを特定する。見つからない場合は、まず候補タイトルを提示し、新規ページを勝手に作らない。
2. `cosense-fetch -r` で対象ページの行配列と現在の SHA-256 を取得する。他者変更を取り込んだ immutable な候補を作る。
3. 長期的に意味がある決定、理由、未解決事項、次の問い、Docs/Granolaへのリンクだけを、関連する行の直下または時系列ページのタイトル直下へ配置する。会議本文の全文やBeeperの通知文は複製しない。
4. Codexが生成した行には `[( …]` を付ける。コード span をその内側へ入れない。人間の発言引用は改変せず、発言者を捏造しない。
5. `scrapbox-write --mode replace --verbatim --expect-sha256 <digest> --dry-run` で候補を固定し、同一本文を一度だけ書く。CAS不一致なら再取得からやり直す。
6. `cosense-fetch -r` で再取得し、対象行、インデント、リンク、`[( …]` を確認する。

例（Scrapbox記法。タイトルは `--title` で渡し本文に含めない）:

```text
[2026/8/27]
 [( [音威子府起業人定例] の決定を Google Docs に反映。次回までに映像試作の共有範囲を確認する。]
  [( 出典: [Granola] / [Google Docs定例メモ]]
```

固有の案件名・相手名・公開可否は、現在の案件ページとlive sourceで再確認してから書く。

## 5. Beeper の通知

通知は成果物ではなく、関係者を安全な正本へ案内する薄い層とする。

### 下書きテンプレート

```text
宛先: <グループ名または相手>
返信先: <既存メッセージID／スレッド。なければ新規話題である理由>
本文:
<会議名>のメモを更新しました。
決定・更新: <一行>
確認してほしいこと: <一行。なければ削除>
Docs: <相手が閲覧できるURL>
Scrapbox: <相手に共有してよいURL。社内限定なら貼らない>
```

- 先に `beeper-send` の検索で同じ会話・依頼・質問を探し、元メッセージへ返信する。
- 社内限定のGranolaリンク、個人情報、未公開ドラフト、交渉メモを、共有範囲を確認せず貼らない。リンク先の権限が宛先にあることを確認する。
- 本文を生成・編集したら、そのターンでは送信しない。宛先、返信先、本文全文を提示し、次のユーザー発言で未変更の本文への明示承認を得る。
- 承認後に宛先・返信先・本文を変えたら、全文を再提示して再承認する。
- 送信後は同じチャットの最新メッセージを読み、自分のメッセージID・本文・時刻・返信先を確認する。HTTP 200や画面のtoastだけでは完了にしない。

## 6. 失敗と停止

| 状態 | 取り扱い |
|---|---|
| Granolaノートが見つからない | 会議名・日付・フォルダ候補を示し、作業を止める |
| Granolaの共有範囲が不明 | 共有変更・リンク貼付を止め、メンバーと権限を確認する |
| Docsが他者更新済み | 差分を保存し、再取得→再編集。上書きしない |
| ScrapboxのSID/CASが不正 | 書き込まず、再認証または再取得を依頼する |
| Beeperの宛先・返信先が不明 | 送信せず、候補だけ提示する |
| 共有範囲が不明 | リンクを本文から外し、権限確認後に再下書きする |
| 送信・更新のreadback失敗 | `完了` と記録せず、どの層まで確認できたかを分けて報告する |

## 7. 最終報告の形

```text
定例メモ共有: <会議名> (<開催日>)
- Granola: <ノート根拠と未確定点>
- Granola folder: <格納先／共有範囲／readback結果>
- Google Docs: <更新した見出し／readback結果>
- Scrapbox: <ページ／配置／readback結果>
- Beeper: <送信済み or 承認待ち／スレッド>
- 未解決: <人の判断・認証・権限・次回確認>
```

`更新した`、`承認待ち`、`送信済み`、`readback確認済み` を一語でまとめない。
