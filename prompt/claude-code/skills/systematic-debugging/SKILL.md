# Systematic Debugging

推測による変更を積まず、観測 → 仮説 → 最小の変更と検証で進める。**状態が改善したことと、根本原因や操作の因果が確定したことを分ける。**

## 最初の判断

- 期待した振る舞い、実際の症状、対象・時刻・環境、既存変更と操作の許可範囲を押さえる。最初から全文ログや全履歴を集めない。
- エラーの該当箇所、再現条件、直近差分、現在の正本状態を狭く読む。警告が原因とは限らない。既存の計測・正常例で切り分けられれば新しい計測を作らない。
- 事実、原因仮説、その仮説を判別できる観測を分ける。再現しない場合や既に正常なら、それ自体を記録し、推測で原因を確定しない。
- マルチコンポーネントでも、未確認の境界だけ追う。入力/出力は状態・時刻・件数等から始め、秘密や私信本文を診断ログへ複製しない。

## 対象に合う検証を選ぶ

### コード不具合

1. 関係するコードと動作する類似例を読み、原因仮説を一つ立てる。必要な契約を理解するまで読み、無関係な参照実装の全読込みはしない。
2. 修正前に、最小の失敗テストまたは再現手順を実行し、**狙った不具合で失敗する**ことを確認する。テストの設定不備を不具合再現と数えない。
3. 原因に対する最小修正を行う。ついでの抽象化や依存導入、無関係な改修を混ぜない。
4. 同じ再現を再実行し、変更した振る舞いに近い回帰テストを通す。型検査・lint・統合確認は影響範囲に合わせて追加する。

### サービス・設定・UIの不調

- 同じ対象・条件のbefore/afterと、対象サービスのcanonical readbackで検証する。表示・プロセス起動・終了コードだけを復旧の証拠にしない。
- 原因未確定でも、証拠を保全できる許可済み・可逆な対処は、戻し方と確認指標を定めて**復旧・緩和**として進められる。恒久修正や原因解明とは呼ばない。
- 対処前から正常だった場合は「今回の操作で直した」としない。現在の成功、過去の欠損や滞留の解消、再発しないことは別々に確かめる。
- 自動テストが適さない対象は、観測可能な再現手順や実機確認を使う。失敗を再現するためだけに本番障害・削除・外部送信を起こさない。

## 効かなかったとき

- 変更が効かなければ、その仮説を棄却または修正する。根拠なく次のパッチを上積みせず、自分の診断用変更を戻す必要も確認する。
- 同じ症状への修正が3回程度続く、各修正が別の問題を生む、大改修を要するなら、前提・観測先・設計境界を再点検する。回数だけでアーキテクチャ不良と断定しない。
- 続行に本人の認証・権限・設計判断が必要なところだけ止める。許可済みの読み取りや安全な切り分けまで一律に承認待ちにしない。

## 終了条件と報告

依頼された振る舞いを再確認し、変更、実測した検証、原因の確度、未解消を簡潔に報告する。再現・検証不能ならその範囲を明示し、「直った」「再発しない」と補わない。

## 複雑な切り分けで使う技法

深い呼出し・層をまたぐ障害、非同期待機、テスト汚染があるときだけ [references/diagnostic-techniques.md](references/diagnostic-techniques.md) の該当節を読む。通常の局所修正では不要。
