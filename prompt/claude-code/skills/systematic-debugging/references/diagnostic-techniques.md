# 必要なときだけ使う診断技法

## 深い呼出しと境界の逆追跡

症状 → 直接の呼出し元 → 不正な値を作った場所と遡り、どの契約がどこで破れたかを特定する。正常例と違う入力・設定・版を比較し、無関係な差分の列挙で止まらない。

既存のログやトレースで分からない境界だけ一時計測を追加する。入力/出力の型・状態・時刻・相関ID等で仮説を区別し、値や本文の全量記録を既定にしない。調査用コード・負荷・保持範囲を元へ戻す必要も確認する。

## 防御を置く場所

入力境界の検証、業務不変条件、環境ガード、診断情報の役割を分ける。修正後に、同じ不正状態が他の入口から到達するかを確認し、必要な境界だけ補強する。

全層に同じvalidationを複製しない。個々のガードは保護する不変条件と反例を示し、テストが実際にその反例を拒否することを確かめる。多層化しただけで「構造的に不可能」とは主張しない。

## 条件を待つ

観測可能な条件や専用のwait/event APIを優先する。ポーリングしかないときは、成功条件・最大待ち時間・適切な間隔/バックオフを決め、期限切れや中断を失敗として区別する。

固定sleep後の値だけで完了を決めず、最新の条件を読み戻す。ただし観測のための間隔そのものを禁止しない。高頻度ループやタイムアウト後の残存処理を増やさず、自分が起動した待機だけを終了させる。

## テストの汚染源を絞る

各試験の前に隔離workspaceの状態を確認し、初めから存在するものを今回の汚染と数えない。ファイル・共有状態・実行順への依存が疑われる場合は、ケース群を二分して絞るか、同じクリーン状態から単独実行する。

試験の終了コードと汚染の有無は別に記録する。テスト失敗を無条件に握りつぶさず、パスの空白に弱いshell列挙や実projectを使った破壊的試験を避ける。原因を特定したら、単独だけでなく問題が起きる組合せ/順序でも回帰確認する。
