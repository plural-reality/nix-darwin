# 書込方式・CAS・LLM装飾・readback

実際に書く前に読む。目的とanchorは[SKILL.md](../SKILL.md)、生成本文の文体は[writing-style.md](writing-style.md)、看板・完了処理は[task-graph.md](task-graph.md)が正本。

## CLIと本文の境界

書込窓口は`scrapbox-write`。stdinは**タイトル行を含めず**、タイトルは`--title` / `-t`、projectは`--project` / `-p`で渡す。

| 方式 | 対応する指定 | 注意 |
|---|---|---|
| 新規本文・全体候補の置換 | `--mode replace`（デフォルト） | `--replace`ではない。既存ページは下のCAS手順を使う |
| 独立した時系列ログの先頭追加 | `--prepend` / `-P` | タイトル直下。質問回答やindex更新には使わない |
| 行の完全保持 | `--verbatim` / `-V` | インデント注入・空行畳み・auto-grayなし。人間行を含む既存ページの局所編集で使う |
| 候補の描画 | `--dry-run` / `-n` | 書込せず、送る行を描画する。成功しても保存・認証成功の証拠ではない |
| 人間の骨子をそのまま保存 | `--no-gray` / `--human` | 人間が書いた部分だけ。AI生成文を人間扱いにしない |

末尾追記は使わず、guardを回避しない。末尾位置が必要な局所配置もCAS付きreplace / verbatimで行う。
通常モードは各行に半角スペース1つを足し、空行を畳む。既存の人間行・tab/space・`code:`ブロックを含む全体候補は`--verbatim`で保持する。

## 候補 → dry-run → 一度の書込 → readback

1. `cosense-fetch -r "exact title" -p PROJECT`で現在のrawを取得する。JSONとして有効で、対象titleと`lines`を持つことを確認し、空出力やエラー文を空ページとして扱わない。未作成ページもHTTP 200のskeletonになり得るため、取得成功と`persistent`を区別する。新規は未作成と確認して候補生成へ、既存は次のCAS手順へ進む。`--exists`のfalseだけで非存在を断定せず、権限・通信失敗なら作成しない。作成直前に既存化していたら取得・統合し直す。この確認を原子的な新規作成保証とは扱わない。
2. 既存ページは、取得した`.lines[].text`の順序付きcompact JSON配列からSHA-256を計算する。line objectやファイル末尾改行をhash対象にしない。
3. 元本文と許可された変更から候補をローカル生成する。編集対象以外の人間行・インデント・コードをそのまま保持し、AI生成箇所だけ手動で装飾する。
4. 同じ候補を`--dry-run`し、意図した行・配置・装飾・既存行保全を差分で確かめる。その候補を固定して一度送る。
5. 対象をcanonical readbackし、候補と実際の行、削除すべき旧矛盾の不在、保持対象を照合する。複数ページはpage / 変更単位で成否を分ける。

既存ページを置換する例（本文ファイルはタイトルを除外し、dry-runが出す行配列にはタイトルがある）:

```sh
cosense-fetch -r "対象ページ" -p plural-reality > raw.json
# raw.jsonの取得成功・JSON・対象title・linesを先に確認
digest=$(jq -cj '[.lines[].text]' raw.json | shasum -a 256 | cut -d ' ' -f1)
scrapbox-write -p plural-reality -t "対象ページ" --mode replace --verbatim --expect-sha256 "$digest" --dry-run < body.txt
# 上の候補を変更せず、一度だけ送る
scrapbox-write -p plural-reality -t "対象ページ" --mode replace --verbatim --expect-sha256 "$digest" < body.txt
cosense-fetch -r "対象ページ" -p plural-reality > readback.json
```

- CAS不一致は他者の更新を保護する停止。再取得した本文へ変更を統合し、候補とhashを作り直す。CASを外して通さない。
- prependのdry-runは**追加片だけ**を描画する。readbackではタイトル直下の追加片に加え、既存部分の保持・重複不在を確認する。全置換ではdry-runの全line arrayと完全一致を確認する。
- URLの出力、tool完了、pipeline末端のexit 0だけで成功にしない。特に途中の取得失敗・空出力を後段の成功で隠さない。
- 書込のtimeout・通信切断などで結果不明なら、再送より先に対象を取得する。反映済みなら再送しない。確認不能なら候補と未確認箇所を残し、書込済みとは報告しない。
- 長い本文や置換も、検証は対象差分と保全条件に絞る。無関係な全ページ検査へ拡張しない。

## LLMが書いた文章のマーク

LLMが生成した文は`[( …]`で手動装飾する。auto-grayがliveにあると仮定して任せず、dry-runとreadbackで確認する。`--verbatim`ではauto-grayが無効なので、混在本文の生成箇所を明示的に装飾する。

| 対象 | 形 |
|---|---|
| 1行の補足 | `[( 根拠は未確認]`。アイコン不要 |
| 複数行ブロック | 先頭行だけ`[codex.icon]`（Claude Codeなら`[claude code.icon]`）、続く生成文も全部灰色 |
| リンクを含む文 | `[( [関連ページ] に条件がある]` |
| タスクのpage object | `[( [⬜ タスク名]]` |
| 必要な行頭見出し | `[(* 見出し]`。既存の`[* 見出し]`へ装飾文字`(`を結合する |

`[( …]`はUserCSSの`.deco-(`装飾であり、リンクではない。内側の`[ページ名]`はリンクとして保持される。
見出しを`[( ** 見出し]`のように星を本文へ入れて表現しない。元が星2個の見出しなら`[(** 見出し]`となる。文中強調を増やさない。

### コード・引用・人間行

- backtickのインラインコードは装飾の外へ出す。例: `[( 設定は]` + インラインコード + `[( で確認した]`。1行に複数の灰色区間があってよく、コード前後の空白・既存provenanceは保持する。
- `code:` / `table:`ブロックは記法とインデントを壊す行単位ラップをしない。通常CLIもこれらのブロックをauto-gray対象から除外するため、生成部分の出自を周囲の説明行で残す。
- 実在する人間の引用`>`は人間の言葉のまま残し、解釈と同じ行へ混ぜない。引用で装飾の開始文字をそのまま出すと構文を壊す場合だけ、引用であることを保って記法を説明に言い換える。
- 人間/LLMの判別はセッションのpatchや実際の発言というground truthで行う。同じScrapboxアカウントのuserIdや文体は著者判定に使わない。
- 既存の人間項目への1行補足は人間項目を残し、直下へ1段下げて`[( …]`。既存LLM行の灰色化も該当箇所だけを変える。

### provenanceと人間による採用

- 実質的な生成は日付と実際のagent iconで出自を残す。ただし日付ブロックを最上位へ新設するのは時系列記録に意味があるページだけ。質問回答や既存命題への補足は該当行の直下へ置く。
- ページにある本人の指示・質問はそのまま保ち、回答を直下へ置く。今回本人が提供した原文を引用として保存する依頼も逐語で反映できる。AIが依頼文を作って`[tkgshn.icon]`付きの発言・署名にしたり、生成文を本人の引用として新造したりしない。
- 人間が装飾を外せば人間の本文色へ戻る。`[( X]` → `X`、`[( [X]]` → `[X]`で内側のリンク/タスクを保持する。AIが本人の採用を推測して装飾を外さない。
- 一括の「人間化」は既存UserScriptの承認UIを使う。CSSだけでは編集者を判定できない。仕組みの導入/修理だけ`scrapbox-llm-marking`へ進む。

## 接続・権限エラー

`SCRAPBOX_SID`は環境へ注入される認証情報。生値を読み出してprompt / skill / Nixへ埋め込んだり、会話への貼付を求めたりしない。
401/403を即座にSID期限切れと決めず、`cosense-fetch --me`等の秘密を表示しない既存手段で、対象projectの権限・稼働環境・認証状態を区別する。必要な対話認証だけ本人に依頼し、その手前の候補生成・差分検査は完成させる。
