# Save to Scrapbox

会話中のコンテンツをScrapboxに書き込むスキル。**Scrapbox 書き込みの canonical な規約はこのページ**。

トリガー: "Scrapboxに保存して", "スクボに入れて", "メモしておいて", "保存しておいて", "save to scrapbox", "ブックマークして", "scrapboxに記載して"

また、googleドライブは、社外に共有するものだけ入れて、基本的に更新されるドキュメントはscrapboxに置いておく。

## 大前提: 新規ページを作るのではなく既存ページに追記する

「Scrapbox に書いておいて」 と言われたら、 まず **そのセッションの作業 context (CLAUDE.md / AGENTS.md / ユーザーが触っているファイル / 直前の議論) からして、 どの既存ページの続きとして書くべきか** を考える。 新規ページ作成は最後の手段。

- 孤立した新規ページは knowledge graph に繋がらず、 メンテされない孤児ドキュメントとして増え続ける。 これが Scrapbox 運用上の最大のアンチパターン。
- 書く前に必ず `scrapbox-context` で関連ページを 1-hop 検索する。 同じトピックの既存ページが見つかれば、 そこに `--prepend` で追記する (タイトル直下、 後述の逆時系列ルールに従う)。
- どうしても新規ページが必要なときは、 (a) 既存の関連ページに `[新ページ名]` を書いて足場を作ってからその先を埋める、 もしくは (b) 既存ページに `[( [⬜ タスク名]]` の page object を書いてからリンク先ページとして膨らませる。
- タスク管理として書くときも、 単独の todo ページを作らない。 既存ページに `[( [⬜ タスク名]]` の page object 行を入れ、 その page object 自体をタスクオブジェクトとして扱う。

## 関連スキル（書く前後で必ず併読）

書き込みフロー全体の責務分担:

| スキル | いつ使うか | 責務 |
|---|---|---|
| `scrapbox-context` | **書く前** | 既存ページ・関連ページを検索して引用・リンクできるようにする |
| `natural-writing` | **書く中** | AI特有の文体パターン（24項目）を回避する文体ガイドライン |
| `scrapbox-llm-marking` | **背景の仕組み** | `[( …]` 装飾を薄く表示する deco CSS と UserScript のセットアップ |

推奨の手順:
1. `scrapbox-context` で既存ページを検索（重複・関連ページを把握、リンク先候補を集める）
2. `natural-writing` の汎用的な AI 文体回避ルールを参照しつつ、本文はこのページの local style contract に従って書く
3. 本ページの「書き方ルール（基本）」+「LLMが書いた文章のマーク」規約で整形する（`[( …]` + `[claude code.icon]`、provenance）
4. `scrapbox-write` CLI で書き込み（必ず `--dry-run` で確認 → append/replace/prepend）

## 対応プロジェクト

| プロジェクト名 | 用途 | 使い分け |
|---|---|---|
| `plural-reality` | 多元現実の法人・チームナレッジベース | 法人の契約・財務・法務・プロダクト・チーム日報。法人/チーム文脈で特に指定がなければこちら |
| `tkgshn-private` | 高木の個人メモ | 「個人の」「プライベートに」と言われた場合 |
| `takalog` | 最機密・自分専用の人物/案件/会話ログ | 人物CRM、個人コンテキスト、会話ログ、過去のAI会話、案件の意思決定履歴 |

書き込み先の判断:
- 法人の契約・財務・法務・プロダクト → `plural-reality`
- 個人の日報・研究メモ・生活メモ → `tkgshn-private`
- 最機密の個人コンテキスト・人物CRM・会話ログ → `takalog`
- 迷う場合は書く前に `scrapbox-context` で3プロジェクトを横断検索し、既存ページの所属に合わせる。

## コマンド

`scrapbox-write` は stdin からページ本文を受け取り、WebSocket 経由で Scrapbox に書き込む。

| モード | フラグ | 動作 |
|---|---|---|
| 全置換 | （デフォルト） | ページ本文を stdin で丸ごと置き換える |
| 末尾追記 | `--append` / `-a` | 既存ページの末尾に stdin を足す。⚠️**通常の追記には使わない**（逆時系列ルールで `--prepend`）。未作成ページのフォールバックのみ |
| 先頭追記 | `--prepend` / `-P` | タイトル直下（ページ上部）に stdin を挿入する。逆時系列の追記用 |
| 逐語 | `--verbatim` / `-V` | 各行を byte 単位でそのまま書く（インデント注入も空行畳みもしない）。既存ページの in-place 書き換えで、インデント・人間が書いた行・`code:` ブロックを崩さず保つための専用モード。stdin はタイトル行を含めない（`--title` が 1 行目になる）。`--replace` と併用が基本 |
| プレビュー | `--dry-run` / `-n` | 書き込まず、実際に送る行を stdout に出す（`SCRAPBOX_SID` 不要） |

```bash
cat <<'BODY' | scrapbox-write -p plural-reality -t "ミーティングメモ"
議題
 項目1
 項目2
BODY
```

- 長い本文・既存ページへの追記は、まず `--dry-run` で出力を確認してから書き込む。
- 成功時に stdout に出る Scrapbox URL を、必ずユーザーに報告する。
- 通常モードの `scrapbox-write` は各行に半角スペース1つを足し、空行を畳む（新規ページ向け）。**既存ページの行を in-place で書き換える**ときは、それだとインデント（tab/space）や `code:` ブロックが崩れるので **`--verbatim` を使う**。現在行を `/api/pages/<project>/<title>` で取得 → 各行を byte 単位で変換（LLM 行だけ `[( …]` で包む等）→ `scrapbox-write --verbatim` で書き戻す。`--verbatim` は行をそのまま送るので、人間が書いた行・コードブロック・インデントを保てる（内部実装は `@cosense/std` の `patch`、後述「既存ページのLLMマーク」）。

## 書き方ルール（local style contract）

Scrapbox記法で書く（Markdownではない）。固定テンプレートを当てるのではなく、対象ページの人間が書いた行から、語彙・粒度・階層・リンクの置き方を読む。

参照する順序は **対象ページ → 同じ種類のページ → 直接のリンク集団 → project 全体**。近い文脈の書き方を優先し、`tkgshn-private` / `plural-reality` の平均像を対象ページへ上書きしない。

### 0. 意味保存は hard gate
- 事実 / 解釈 / 仮説 / 質問 / 提案 / 決定 / タスク / 引用 / 出典の種類を変えない。
- 数字、固有名詞、具体例、例外、反証、不確実性、未解決の問い、出典を「読みやすさ」のために丸めない。
- 本人の訂正や反対意見がある場合、古い AI の主張へ補足を足すだけで済ませず、主張自体を訂正後の形へ直す。
- 確認済み / 解釈 / 可能性 / 不明 / やりたい / 決定済み / 次の行動を混同しない。断定の強さを勝手に上げない。
- 人間の既存行は byte 単位で保存する。AI らしい文体であることを著者判定の根拠にしない。

### 1. 1行は1つの意味命題
- 文字数で機械的に切らない。読んだ人が「この行は何を言っているか」を1つ答えられる単位にする。
- 理由 / 具体例 / 反例 / 但し書き / 次の問いは、親となる命題の直下へネストする。
- 親子関係を説明できない行は、無理に子行へせず同じ階層に置く。
- 長い説明をそのまま段落にせず、意味命題とその根拠へ分ける。ただし短文化そのものを目的にしない。

❌ パラグラフ + 文中強調:
```
[✅契約] に基づく支払いについて、青山が米国在住である点を踏まえると [** 非居住者] に該当し、[** 源泉徴収義務] が発生する可能性がある。
```
✅ 箇条書きに分解（強調なし）:
```
背景
 [✅契約] に基づく支払い
 青山は米国学生ビザで在住 → 日本の税法上は非居住者に該当
 非居住者への著作物使用料 → 源泉徴収義務が発生する可能性
```

### 2. インデントの仕組み・空行
- `scrapbox-write` は各行に半角スペース1つを足す。行頭スペースなし → インデント1段。ネストは行頭スペースを足す。
- **セクション間の空行は使ってよい**（中黒は出ない）。読みやすさのため適度に空ける。

### 3. report boilerplate を作らない
- 「概要 / 背景 / 結論 / ポイント / 問題点 / まとめ」を機械的に並べない。観察 → 理由や制約 → 判断や未確定点が読めるなら見出しは不要。
- 「調査した」「整理した」「以下にまとめる」のような前置き、同じ結論の言い換え、網羅感を出すだけの列挙を削る。
- 具体値、理由、例外、失敗、次に直す時の制約、続きの問いは残す。
- タイトルは内容を直接表す命題 / 問い / タスクにする。「概要」「まとめ」「調査レポート」のような汎用タイトルを作らない。

### 4. 自然な日本語にするが、本人を演じない
- ページ内の語彙や文末のリズムには合わせるが、AI が「俺」「w」や `[tkgshn.icon]` を足して本人になりすまさない。
- 断片的なメモは、意味が通る範囲で断片のまま残してよい。説明文へ膨らませない。
- `tkgshn-private` では探索中の粗さや未完了を消さない。`plural-reality` では発言者、決定、担当、状態の区別を消さない。

### 5. 強調（太字）を文中で使わない
- 文の途中の語を `[* …]` `[** …]` `[[ …]]` で強調しない。不自然になる。
- 構造はネストで表現する。見出しが要るときだけ行頭ラベルにする。

### 6. テーブル内では強調を使わない
- テーブルのセルでは強調記法が効かない。プレーンテキストで書く。
- `table:名前` の次行から、1段深いインデント + TAB区切りで行を書く。

### 7. `#` を使わない
- `#3` のような番号・記号に `#` を使わない。Scrapbox ではタグ/リンク化されてしまう。
- 番号は `No.3` `3番目` のように書く。

### 8. ステータス記号（TODO）
チェックや進捗には絵文字を使う（`[ ]` `[x]` はリンク記法と衝突するので使わない）。
- `⬜` タスク / `⏳` 進行中 / `⏹️` 停止 / `☑️` 完了

#### 完了は追記ではなく、task graph の状態遷移

`⬜` / `⏳` / `⏹️` / `⌛️` で始まる task page に「完了した」という本文を追記しただけでは完了ではない。タイトル、backlink、ToDoカンバンの index 行が古いまま残り、今回のように実作業とドキュメント状態が分離する。

完了証拠を確認したら、次を1つの closure transaction として扱う。

1. canonical task page と `ToDoカンバン` の exact task object を live readback する。
2. `scrapbox-rename <project> "<旧status title>" "☑️<同じtitle>"` で既存ページを in-place rename する。新タイトルへの別ページ作成は禁止。
3. canonical task page の stale な `next_action` / `現在の境界` / blocker を削除または完了事実へ置換し、証拠を関係する位置へ記録する。
4. `ToDoカンバン` の exact task 行を `☑️` へ揃え、直下の子行を `status:: done ／ completed:: YYYY/M/D ／ evidence:: ...` に置換する。古い `next_action` は残さない。
5. 両ページを再取得し、次の全 invariant を確認する。
   - task page の先頭行が `☑️`
   - ToDoカンバンに旧status titleが0件、新titleが1件
   - task直下が `status:: done` と `completed::` と検証済み evidence を持つ
   - stale な `next_action` / 再認証待ち / 未実行境界が残っていない

`scrapbox-write` は、open status title に先頭6行内の完了証拠を書こうとすると fail closed する。非closureの履歴引用だけは `--allow-open-task` で明示的に通せるが、そのフラグでtaskを完了扱いにしてはいけない。

**禁止:** open titleへの `--prepend` 成功と、その本文の再読込だけをもって「Scrapboxも更新済み」と主張すること。

### 9. リンクは意味構造として置く
- 書く前に Scrapbox を検索し、実在する exact canonical title を使う。表記揺れの新ページを作らない。
- 出典となる親ページは `from [元ページ]`。個別の関連ページは、その関係を述べた命題の直下へ置く。質問への回答は質問の直下へ置く。
- ページ全体ではなく正確な箇所を根拠にする必要がある場合は block link を使う。外部リンクは `[URL 内容が分かるラベル]`。
- 名詞が登場するたびにリンクする「noun-link spam」はしない。リンクを外しても文章の構造が同じなら、そのリンクは不要な可能性が高い。
- 引用は `>` のまま保存し、AI の解釈と同じ行へ混ぜない。発言者を変えない。

### 書込前の自己検査
1. 意味の種類や断定の強さを変えていないか。
2. 各子行を理由 / 例 / 反例 / 但し書き / 次の問いのどれかとして説明できるか。
3. report boilerplate を削っても、具体値・例外・不確実性・出典が残っているか。
4. AI が本人の口調や icon を捏造していないか。
5. リンク先は実在する canonical title で、関係する命題の近くにあるか。
6. 対象ページの人間行の方が、この skill の例文より優先されているか。

## LLMが書いた文章のマーク（最重要）

人間が書いた文章と LLM が書いた文章を視覚的に区別する。LLM（あなた）が生成した文は **`[( …]` 装飾**で囲む。**これは agent（あなた）の責務であり、省略不可。**

> ⚠️ **auto-gray を当てにしない（最重要・再発防止）。** 「`scrapbox-write` が `[( …]` を自動付与する」設計は nix-darwin 側にあるが、**実機の `scrapbox-write.mjs`（nix store の live 版）に未反映のことがある**（darwin-rebuild の switch 漏れで旧版が動き続ける。実際 2026-06-02 に、これを信頼して素テキストのまま書き込み AI文が灰色化されない事故が再発した。さらに同日、別タスク（火災保険PDFの記録）で `--verbatim --append` を使い、prepend も手動マークも怠る**2度目の事故**＝そもそも追記前にこの skill を読まなかったのが根因）。だから **agent は追記前に必ずこの skill を読み、自分で全 LLM 行を `[( …]` でマークし、`--prepend`（タイトル直下・逆時系列）で stdin に渡す**（auto-gray が live でも冪等なので二重にならない。`--append` は使わない）。
> - **書込後に必ず self-verify**: `/api/pages/<project>/<title>/text` を取得し、自分が足した LLM 行に `[(` が付いているか grep で確認する。付いていなければ `--verbatim` で貼り直す。
> - **追記は `--prepend`（タイトル直下）。`--append` は使わない**（後述「逆時系列」）。
> - 人間の骨子をそのまま保存するときだけマーク無し（`--no-gray`/`--human` が live ならそれ、無ければ素のまま渡す）。
> - 既存ページの in-place 書換は `--verbatim`＝**LLM 行を手動マーク**して貼り直す。
> 以下の記法は「LLM 行に付けるべき形」の定義。

- `[( …]` は UserCSS `.deco-(`（薄く表示する装飾）。**リンクではない**ので幽霊ページは作られず、**中に `[リンク]` も入れられる**（例 `[( [冷蔵庫]: 27,000円]`）。
- **backtick インラインコードは `[( ]` の外に出す**: Scrapbox の装飾ブラケットの内側では `` `code` `` が等幅表示にならず壊れる。コードを含む行は、コード span ごとに装飾を閉じ、プレーンな各区間を個別に `[( …]` で包む（**1行に `[( …]` が複数になってよい**）。リンク `[Page]` は装飾内に残せる（分割対象は backtick のみ）。
  - 壊れる: `[( statusline に `/rename` で…実証] \`#hash\``
  - 正: `[( statusline に] \`/rename\` [( で…実証] \`#hash\``（コードは装飾の外、前後の空白は保持）
  - 末尾の provenance（`` `#hash` ``・時刻）は元から `[( ]` の外なので従来通り。
- **アイコンの付け方**:
  - 1行だけの LLM 記述 → `[( …]` のみ（装飾で LLM とわかるので**アイコン不要**）。
  - 複数行にわたる LLM ブロック → **先頭行にだけ agent アイコン**を付け、続く行も**全部 `[( …]`** で書く。
- **agent アイコンは書いた主体で使い分ける**:
  - Claude Code が書く → `[claude code.icon]`
  - Codex が書く → `[codex.icon]`
- **タスクは page object 化する**: AI が生成するタスクは `[( [⬜ タスク名]]` のように内側を `[…]` リンクにする。そうしないと他ページから参照できる object にならない。
  - 例: `[( [⬜ 椅子を中古で探す]]` / `[( [⏳ 見積もり依頼中]]`

### provenance（出自を必要十分に残す）
実質的な生成は、日付と agent icon で出自を残す。人間の実際の指示や質問が既にページにある場合だけ引用を保持し、回答はその直下へ置く。AI が `[tkgshn.icon]` 付きの指示を新しく作らない。
```
[2026/05/29]
 >[tkgshn.icon]による指示:
 > 「<ユーザーが出した実際のプロンプト>」
 [( ここからの概要は Claude Code が生成][claude code.icon]
  [( 要点を箇条書きで…]
  [( [関連ページ] への参照もリンクのまま装飾できる]
```
- 日付ブラケット `[YYYY/MM/DD]` は、時系列の記録自体に意味があるページで最上位に置く。質問回答や既存命題への補足では、日付ブロックを新設せず該当行の直下へ置く。
- 実在する指示の引用 `>` 行は人間の言葉なので装飾しない。LLM が生成した行だけ `[( …]`。
- プロンプト引用に `[( ` や `[…]` をそのまま入れると壊れるので、その2文字は引用内で言い換える。

### 既存ページのLLMマーク（人間の記述への補足）
人間が書いたページに LLM が補足した箇所だけをマークする。
- 人間/LLM の区別は ground truth で判断する（同一 Scrapbox アカウントで書くと行の `userId` では判別できない。セッションログや実際の patch 内容で確定する）。
- 人間の項目への単行補足は、項目はそのまま残し、**1段下げて `[( …]`**（単行なのでアイコンなし）:
```
[ブレインスリープのAll in One]
 [( 新品: 77,000円 / 中古: 3.0〜4.5万円目安]
```
- 複数行の LLM ブロックは先頭にアイコン、全行 `[( …]`。
- in-place 編集なのでインデント保持のため `scrapbox-write --verbatim` を使う（現在行を取得 → 該当行だけ `[( …]` に変換 → 全行を `--verbatim` で書き戻す）。`--verbatim` 無しの通常モードはインデントを崩すので使わない。

### 人間が編集したら人間の色に戻す
- `[( …]` の装飾を外せば普通の人間テキスト色になる。手動なら `[( X]`→`X`、`[( [X]]`→`[X]`（リンク/タスクは保持）。
- UserScript の「人間化」ボタンで選択行を一括変換できる（`/tkgshn-extension` に設置）。CSS 単体では編集者を判定できないため、外すのは UserScript か手動。

## 記法リファレンス
- 見出し（行ラベル）: `[* 見出し]`（大きく: `[*** 見出し]`）
- リンク: `[ページ名]` / 外部リンク: `[URL 表示名]`
- アイコン: `[tkgshn.icon]` / `[claude code.icon]` / `[codex.icon]`
- LLMマーク装飾: `[( テキスト]`（`.deco-(` = 薄表示。リンク内包可）
- 箇条書き: 行頭スペースでインデント
- 引用: 行頭 `>`
- コード: インライン `` `code` `` / ブロック `code:filename` + インデント
- テーブル: `table:名前` + 1段深いインデントで TAB区切り行
- 打ち消し線: `[- 取り消すテキスト]`

## URL・参考リンクの書き方
- 単に URL を貼るだけなら、メタデータが無くても URL のままでよい（Scrapbox 側でカード表示される）。
- 「参考リンク」として載せるときは、WebFetch でページタイトル（メタデータ）を取得し `[URL タイトル]` 形式にする。取得できなければ URL のまま。

## 追記・改訂のルール

### GTDのcanonical contract

GTDは1つの巨大ページに集約しない。正本を増やさず、同じScrapbox graphを次の3種類のviewへ分ける。

- `ToDoカンバン`: 完了条件が明確で、実行可能な次アクションだけを置くcurated index。**階層はScrapbox本来の字下げで表す**（星の数は見た目の強調でしかなく、意味を持たせない）。行の形は3種類だけ:
  - `[** 名前]`（星2つ以上） = 升目の見出し。字下げが1段深い行はその中身。
  - 素のテキスト = その升目が何かを言う一言。見出しの直後に1行だけ置く。
  - `[ページ名]` = カード。直前の見出しに属する。素のテキストのタスクは書かない。

  現在の升目（2026-08-19 更新）:

  ```
  Inbox        分類が必要なもの
    Dependency 前のタスクが終わるまで着手できないもの
  Todo         いま自分で動かせるもの
    @5分・スマホ / @PC（10分 / 30分 / 1時間〜） / @家 / Someday
  Waiting for  何かしらに委譲しているもの
    Someone / System / AI
  Scheduled    時間で発火するもの
  Triggered    その場所に着いたら発火するもの
    コンビニ / 郵便 / ダイソー / @構想日本 / @音威子府
  ```

  - `Scheduled` の中の `今日` / `明日` / `今週` / `もっと先` は**升目として書かない**。カード名の先頭が `yyyy/mm/dd` なら表示側が日付から導出する（レーンにすると毎日手で動かす二重管理になる）。日付を持つカードは `⬜2026/08/28 …` の形に正規化する。
  - `Inbox` は分類前の置き場。完了条件を確定できるまで留め、確定したら該当の升目か個別pageへ送る。
- `プロジェクト看板`: 複数アクションを要する進行中の成果だけを置くcurated index。次アクションや進捗ログを複製しない。
- 個別task/project page: 完了条件、次の一手、blocker、期限、履歴、証拠のcanonical source。看板へ詳細を展開しない。

両看板は相互リンクする。タスクの詳細化は看板行を長くするのではなく、exact page objectのリンク先で行う。完了条件を確定できない気がかりや複数工程の成果は、ToDoへ残さず個別pageまたはプロジェクト看板へ送る。

看板は時系列ログではない。独立したCodex/Claude進捗ブロック、日次報告、横断レポートを置かない。agentの作業待ち行列は `Waiting for` > `AI` の中に置き、`[claude code WIP.icon]`はtrailing textなしの構造markerだけとし、agentの作業説明はcanonical task pageへ置く（`Agent Queue` という独立レーンは 2026-08-19 に `AI` へ統合した。待ち先がAIであることは `Waiting for` の一種であって別軸ではない）。

2看板を書き換える唯一の手順:

1. `cosense-fetch -r`で取得した`lines`から`.lines[].text`だけを順序どおりに抽出し、`JSON.stringify`相当のcompact JSON配列をSHA-256へ流す。例: `jq -cj '[.lines[].text]' raw.json | shasum -a 256 | cut -d ' ' -f1`。line object全体や末尾改行、`shasum`のファイル名欄を`--expect-sha256`へ含めない。
2. 人間行をbyte単位で保持した全体候補をローカル生成する。
3. `scrapbox-write --mode replace --verbatim --expect-sha256 <digest> --dry-run`で候補を固定する。
4. 同じimmutable bodyを`--dry-run`なしで一度だけ送る。`prepend` / `append`は禁止。
5. `cosense-fetch -r`で再取得し、dry-runのline arrayとの完全一致を確認する。

`scrapbox-write`はこの境界をfail closedで強制する。CAS不一致なら他者の変更を候補へ統合し、再取得からやり直す。

### 原則: 内容の関係が読める位置へ置く

配置は `prepend` / `append` の都合ではなく、ページ内で何に属する情報かで決める。

- 時系列の living page に新しい独立ログを足す場合だけ、日付ブロックをタイトル直下へ `--prepend` する。
- 既存の質問への回答、命題への理由・例・但し書き、ユーザーの訂正は、該当行の直下へ1段下げて置く。
- 構造化 index / kanban では `prepend` も `append` もしない。状態はexactなtask/page-object行で表し、理由・期限・次の一手・詳細・履歴・証拠はcanonical task pageに置く。
- ToDoカンバンへ横断レポートや日次まとめの独立 AI ブロックを作らない。run summary は当日の daily page へ置く。
- anchor を特定できない場合は、無関係な位置へ仮置きせず、canonical page または daily page へ書く。必要なら書込みを止めて anchor を確認する。

### 部分的な差し替え（参考リンク・一文の更新）
古い記述を打ち消し線で残し、1段下げて日付付きで追記する。
```
参考リンク
 [- 旧ソース: ○○のガイド — https://old.example.com]
  [2026/5/29] 追記: [https://new.example.com 新ソース: ××の解説] に差し替え
```
- 打ち消し線の中にライブなリンクを入れ子にしない。旧リンクは「タイトル — URL」の素のテキストで打ち消す。

### 既存ページに [( …] LLM ブロックを足すとき
1. 新ブロックは、時系列ログなら title 直下、回答や補足なら対象行の直下、kanbanなら exact task anchor の直下に置く。
2. ページに既に同じ意味の旧ブロックが残っているなら、in-place patch で旧ブロックを削除し、正しい位置へ新ブロックを挿入する。単純な prepend / append で重複させない。
3. 関連ページへの波及: 概要が変わったら、`[…]` でリンクしている関連ページに残る古い情報も打ち消し線で消し、その下に `[このページ名] に追記あり` と書いて誘導する。

## その他の注意
- タイトル行は本文に含めない（`--title` で渡したものが自動で1行目になる）。絵文字付きタイトルも `--title` 側に書く。
- 追記と全置換を混同しない。時系列ログの追加だけ `--prepend`、丸ごと差し替えはデフォルト（replace）、既存行の局所配置・in-place 書換は `--verbatim`。位置に意味があるページで `--prepend` / `--append` を使わない。

## ツイートURLの場合

ツイートURLを保存する場合は、twitter-bookmark API 経由:

```bash
curl -s -X POST http://localhost:3000/api/bookmark \
  -H "Content-Type: application/json" \
  -H "x-api-key: $TWITTER_BOOKMARK_API_KEY" \
  -d '{"url": "ツイートのURL"}'
```

前提: `twitter-bookmark` サーバーが起動中であること。
