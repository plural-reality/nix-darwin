# Save to Scrapbox

Scrapbox書き込みのcanonicalな規約。目的に合う既存の文脈へ、意味と著者を保って反映し、実際に保存された差分を確かめる。

## 先に保つもの

- 事実・解釈・仮説・質問・提案・決定・タスク・引用・出典を混同しない。数字、固有名詞、具体例、例外、反証、不確実性、未解決の問いを丸めず、断定の強さを勝手に上げない。
- 本人の訂正は旧AI主張自体に反映する。矛盾した旧主張を残して新しい結論を足すだけにしない。
- 人間の既存行はbyte単位で保全する。明示された編集対象以外を再執筆せず、文体や同一アカウントのuserIdから著者を推定しない。
- AI生成文を人間の発言にしない。`[tkgshn.icon]`付きの指示・引用・署名を新造せず、実在する引用だけを保つ。生成した文はLLM装飾で区別する。
- exact canonical titleと依頼された保存範囲を保つ。孤立した重複ページ、競合する正本、無関係な全ページ改稿を作らない。

## 目的 → 対象とanchor → 書込方式

まず依頼と直前の作業context（AGENTS.md / CLAUDE.md / 対象ファイル / 議論）から、何を変えたいかを決める。

| 目的 | 配置・方法 |
|---|---|
| 既存の質問への回答、理由・例・留保の補足 | 対象行の直下へ1段下げる。rawから局所差分を作り、CAS付きreplace / verbatim |
| 旧AI主張の訂正・重複の整理 | 当該節の主張自体を訂正し、旧矛盾・重複を残さない。CAS付きreplace / verbatim |
| 時系列living pageへの新しい独立ログ | 日付ブロックをタイトル直下へprepend。既存命題への補足とは区別 |
| 構造化index・看板の状態更新 | exact task / page objectだけを更新。[GTDのcanonical contract](#gtdのcanonical-contract)を読む |
| 明示された新規ページ・ハブと子ページ | 新規作成を妨げず、既存の親・関連ページとリンクしてgraphへ繋ぐ |

- 対象project / pageが指定済みなら、そのrawを読むところから始める。既知の原文・exact titleを使えるのに、3プロジェクト再探索や一律1-hopを繰り返さない。
- 対象やリンク先が未解決なら`scrapbox-context`で候補を探す。未知候補の探索は`plural-reality` / `tkgshn-private` / `takalog`の3つを対象にし、候補タイトルから必要な本文だけ読む。
- 新規が必要でも孤児ページにしない。既存の親に`[新ページ名]`の足場を置いて繋ぐ。タスクは単独の文章でなく`[( [⬜ タスク名]]`のpage objectで扱い、看板へ載せる実タスクはリンク先の本文・完了条件を先に確定する。
- anchor不明のまま無関係な場所へ仮置きしない。依頼に合うcanonical page / daily pageで解決できなければ、その一点だけ確認する。
- 末尾追記のguardは維持する。末尾という位置が必要な局所編集も、全体候補を作ってCAS付きreplace / verbatimで反映し、追記モードの例外を増やさない。

## 保存先

| project | 用途 |
|---|---|
| `plural-reality` | 法人の契約・財務・法務・プロダクト・チームナレッジ・チーム日報 |
| `tkgshn-private` | 個人の日報・研究・生活メモ。「個人の」「プライベートに」の指定 |
| `takalog` | 最機密の個人コンテキスト・人物CRM・会話ログ・過去のAI会話・案件の意思決定履歴 |

迷うときは関連する既存ページの所属を確認する。更新される知識は原則Scrapbox、社外共有用の成果物はDriveへ置く。受領原本をDriveに保存する依頼では、原本をSCBへ複製せず保存先・受領事実・未受領の区別を記録する。保存依頼を公開・共有権限変更の許可と解釈しない。

## 必要な詳細だけ読む

- **本文を生成・改稿する時**: [書き方・リンク・意味階層](references/writing-style.md)。対象ページの人間行が文体の第一基準。
- **実際に書く時**: [書込方式・CAS・LLM装飾・readback](references/write-operations.md)。`scrapbox-write`を使い、同じ候補のdry-run → write → canonical readbackで確認する。
- **タスク・看板を変更する時**: 下のGTD契約を追加で読む。
- `scrapbox-llm-marking`はCSS・UserScript・承認UIを導入/修理する時だけ。通常書込でそのセットアップ全体や`natural-writing`の一般論を毎回読み込む必要はない。

### GTDのcanonical contract

`ToDoカンバン` / `プロジェクト看板` / task pageの変更、完了処理には、[task graph・2看板・closure transactionの全契約](references/task-graph.md)を読む。看板は時系列レポートではなくcurated index。完了本文の追記だけでは完了にしない。

## レビューと結果

- 許可済みの小さな保存・訂正は、毎回承認を取り直さず進める。複雑な文体・構造の再設計で本人判断が必要なら、ルール説明だけでなく実物のbefore / afterを少数示す。採否・自由文・追加スコープを区別し、未評価を賛成と数えない。
- 最後はpage / 変更単位で「反映した内容・URL・検証・未反映または未確認」を簡潔に返す。URLが出た、toolが終わった、pipeline末端が0だった、だけでは保存済みとしない。
- 結果不明なら先に対象を再取得する。readbackできなければ候補を残して未確認とし、二重書込になる再送をしない。

## ツイート / X URL

既存の`twitter-bookmark`取り込み経路を使う。固定のlocalhostポートを推測せず、その正本repo / 運用手順で現在の稼働先と呼出し方を確認する。保存のためにサービス本体・配備先・認証方式を変更しない。
