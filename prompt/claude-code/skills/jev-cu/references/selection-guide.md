# Computer Useでの選び方

調査日: 2026-09-29。Jevを万能な高速化として採用しない。新しい選択肢の導入を自動的に許可する文書ではない。

## 今回の判断

- 決めること: 小さな判断をJevへ任せる条件と、別経路を優先する条件。
- 制約: 既存の認証・操作範囲を守り、成功の読戻しを維持する。新しいdriverや権限を無検証で追加しない。
- 既知: OpenJEV経由の電卓1操作は4.883秒、直接CUAは3.316秒。Jev通信は0.779秒。各1回、同じ0→6、両方成功。モデルの計画時間・外側のtool往復は含まない。

## 選択順序

| 対象 | 最初に検討する経路 | 理由・限界 |
|---|---|---|
| データ取得・検索・対象IDでの更新 | 既存のnative API/CLI/typed tool | UI描画や要素探索を避けられる。許可範囲・readback・再試行契約が適合する場合だけ |
| 安定したフォーム、既知のボタン | 直接AX/DOM操作、短い既知手順のまとめ実行 | 判断モデルを挟む必要がない。遷移後の古いindexや無条件sleepを使わない |
| 意味で選ぶ少数の候補、繰返し分類 | Jev/OpenJEVの限定判断 | 大きなモデルとの判断往復を減らせる可能性。候補を構築する費用と低信頼時の返却も測る |
| 画像・canvas、ラベルのないUI、空間関係 | 利用可能な視覚対応Computer Use | このJev実装はテキスト候補のみ。視覚モデルの優位はこのMacでは比較未実施 |
| 未知の長い手順、自由文生成、例外処理 | 親の汎用モデル + 狭い実行ツール | 計画や生成と候補選択を分ける。全手順をJevに押し込まない |

ブラウザのPlaywright locatorはrole/nameによる要素特定と自動待機を提供する。ただし、このMacでは公開されたCUA内のAPIだけを使い、別のChrome/CDP経路を増やさない。Macアプリはapp-scoped AXを使う。

## Jevの効果が出る仮説

同じ既知の候補から選ぶ各判断について、削減できる親モデルの往復時間が、Jev通信・追加観測・誤りの復旧・低信頼時の親への返却を上回る場合に有利となり得る。画面読取りやサイト待ちが支配的なら、推論だけ速めても改善幅は小さい。

例: 多数の短文の分類、既知の担当先への振分け、抽出済み候補の意味による照合。Computer Useでは、AXから絞った候補の意味選択が繰り返される画面が候補。これらは適性の仮説であり、現実装で速度優位を実証したケースではない。

独立した複数の質問を一回のAPIへまとめる設計は有望だが、現在のrunPhaseは単一Choice。異なる時点の画面や依存する次の操作を先読みして一括実行しない。読戻しと権限境界を省いて速度を作らない。

## 測定と採用条件

同じ初期状態・成功条件で、直接実行、親モデルが都度判断、Jevによる限定判断を比較する。計画、画面取得、通信、操作、読戻し、返却・復旧を含む総時間を区別して記録する。複数の代表タスクで成功率と誤操作、中央値、裾の遅延、費用を比較する。1回の電卓試験から全般の倍率や最良モデルを結論しない。

現在の0.8閾値は保守的な初期値であり、ユーザー業務で校正済みではない。confidenceは正答率の保証ではない。OpenJEVのopenjev別名は可変であり、モデル変更時には比較をやり直す。
