# 意思決定文書のテクニカルライティング

「読み手に決めてもらう」ための文書の規範。エッセイ・解説・思想メモは `japanese-tech-writing`（一文一行の散文規範）に従う。この規範は、方針・テーマ・採否を相手に判断してもらう資料（多くは Google Docs）に使う。散文で流す書き方は、意思決定資料では読み手が決めにくくなるため使わない。

## 使いどころ

- 使う：提案書、検討メモ、決裁・相談資料、方針の整理（例：会議テーマの選定、施策の採否、予算配分の提案）。
- 使わない：エッセイ、ブログ、思想メモ、解説記事 → `japanese-tech-writing`。

## 適用範囲（全媒体で遵守）

このスキルの**コンテンツ規範（列挙と改行・表の凡例・平易化・ネイティブリンク・事実の正確さ・トーン）は、意思決定文書に限らず、対外・作業成果物のすべてで遵守する**。Google Docs だけの話ではない。

- メール：結論ファースト、番号マーカー不使用、同列3つ以上は改行、生 URL でなくネイティブリンク。送信は下書き→ブラウザで人間確認（自動送信しない）。文体は宛先別ガイドに従う。
- スライド：印刷前提（白黒コピー）で作る（背景ベタ・色依存グラフを避ける）。体裁の正本は `plural-reality-design-system`。文章は本スキルの規範に従う。
- カレンダー予定・リマインダー：タイトルと本文にも同じ規範を適用（番号マーカー・中黒の並列を避け、要点を素で書く）。予定には位置情報を入れる。振分と生成メカニクスは memory の Apple Calendar / Reminders 項に従う。
- Scrapbox：記法は Scrapbox 側に従いつつ、列挙・改行・平易化の規範は本スキルを適用する。

構造（結論ファーストのサマリー・決定志向の見出し・役割ラベル）は「読み手に決めてもらう文書」でのみ必須。**書式・語彙・事実性の規範は媒体を問わず常に効かせる**。

## トーン

相談。断定・宣告調にしない。ただし明確な仮説（推奨）を持ち、言い切る。「仮説」で濁して逃げない。冒頭で推奨を示し、末尾で「認識のずれや違和感があれば教えてください」と開く。

## 型（上から順に効く）

- **結論ファースト**：冒頭に「サマリー」を置き、推奨を一文で言い切り、根拠を箇条書きにする。「理由は3点あります」と水増しせず「推す理由は以下3点：」で本題に入る。
- **見出しは決定志向の名詞句**：内容を特定する（「前提：この会議の位置づけ」「検討したが、やらなかったこと」）。手順名や情報量のない見出しにしない。読めば節の中身が分かる語にする。
- **各セクション冒頭に一文の概要**を素で置く。「要点：」のようなラベルは付けない（冗長）。
- **段落は役割ラベルで導く**：参考／注意点／ねらい／効果／凡例。散文で流さず、ラベルと箇条書きで構造を見せる。
- **理由・条件はタイトな箇条書き**：フル文でなく要点句。
- **読み手に言葉を合わせる**：専門語（例「ゼロサム」）を対象読者（例：70代の住民）に通じる平易語に置く（「今ある資源の中で組み替える」）。どうしても使うなら括弧で補足するか脚注に降ろす。
- **余白を惜しまない**：改行と段落分けで詰まりを避ける。「参考」「注意点」は独立した段落にする。一段落に詰め込まない。改行が少ないと読み手に厳しい。

## 列挙と改行

- **列挙に番号マーカー（`(1)` `（1）` `①` など）を行頭に使わない**。順序や対応づけが本質でなければ箇条書き（各項目を改行）にする。順序が要るときも、見出しスタイルの自動採番や本文の語（「1つ目は」）で表し、`(1)` を打たない。
- **同じ資格の項目が3つ以上あるときは、読点や中黒で一行に詰め込まず、各項目を改行して箇条書きにする**。2つまでなら一文中に読点でつないでよい。
- **装飾のための記号を使わない**。`■` `▼` `●` `◆` `▶` `※` `★` などの記号を、行頭マーカー・見出し・強調・区切りに使わない。意味のない記号は削る。見出しや強調が要るときは**太字**にする（Scrapbox なら見出し記法 `[* ]`／AI灰色行なら `[(* ]`。`[( ■ 見出し]` は禁止で `[(* 見出し]` にする）。
- **区切りにダッシュ（`――` `—` `―`）を使わない**。「A ―― B」は、言い換えなら句点で二文に、同格・補足なら括弧に、ラベルと説明なら全角コロン `：` に置き換える。
- この整形は Google Docs・スライド・Scrapbox など、媒体を問わず適用する。

## 機械チェック層（LLM に任せず script で厳密判定）

レビューは2層に分ける。決定論的に判定できる書式違反は、目視でなく linter で厳密に落とす（LLM は見落とす）。意味層（結論ファースト構造・トーン・平易化・出典の裏取り・中黒が並列か固有名詞か）だけを LLM が担う。

- linter: `scripts/content-lint.py`（stdin フィルタ・stdlib のみ）。ERROR=装飾記号／ダッシュ `——`／丸数字 `①`／番号マーカー `(1)`。WARN=全角スラッシュ／生URL。
- 使い方：
  - Markdown / テキスト: `content-lint.py doc.md`（または `cat doc.md | content-lint.py`）
  - Scrapbox raw: `cosense-fetch "題" -p PROJ -r | jq -r '.lines[].text' | content-lint.py`
  - 自己検証: `content-lint.py --selftest`
- **対外・作業成果物は書き出し前にこの linter を通し、ERROR を0にする**。warn は媒体依存（Scrapbox の生 URL は自動リンクされ許容）なので文脈で判断する。

## 表

- 記号を使うなら **凡例を必ず添える**（例：◎ 強く合致／○ 合致／△ 条件つき／✕ 合致せず）。
- **列名・専門語を定義する**。「見立て」より「第1回での扱い」のように、読めば分かる語にする。ジャーゴン（例「再フレーム」）をセルに置かない。ニュアンスは注記か別列で平易に書く。
- **記号は字幅・大きさを揃える**。●と◎の混在など、大きさが不揃いに見える組み合わせを避ける。日本の資料では ◎○△✕ が読み手に馴染む。

## 関連資料

- 生 URL の羅列でなく、テキストに **ネイティブリンク**を張る（Google Docs なら HTML の `<a>` でインポートする）。
- 根拠のスライド・データ・会議セッション・前例の一次ソースを貼り、相手が裏取りできる状態にする。

## 事実の正確さ

- 数値・固有名・引用は一次ソースで裏取りする。ASR（自動文字起こし）由来の語は誤りを疑う（例「汽車」→ 実際は「電車」）。
- 裏が取れないものは、一覧に載せず「未確認・要照会」と注記して落とす。断定で滑らせない。

## Google Docs で出すとき

- ページ分けなし（pageless）／ブックマークを入れない／区切り線を使わない／番号ベタ打ちでなく見出しスタイル・自動採番。
- 生成手順（HTML インポート ＋ pageless）は memory の [[reference_gws_google_doc_creation]] を参照。canonical な体裁ルールは memory の [[feedback_external_writing_norms]]。

## 由来

2026-07 の音威子府くじ引き住民会議テーマ選定資料で、ユーザー自身の編集から抽出したパターン。「japanese-tech-writing はエッセイ向きで、意思決定を求める文書には向かない」という判断に基づく。
